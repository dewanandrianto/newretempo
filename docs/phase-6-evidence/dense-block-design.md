# Phase 6 — dense-block retrieval and publication design

## Verdict: NOT PROVEN for unrestricted canonical history under the existing bounds

**Architecture proposal only; not an implementation or release approval.** Incremental private staging can remove the **16 target events per block** scheduling barrier when every required RPC object is retrievable. It cannot guarantee progress when a required single receipt exceeds **524,288 decoded response bytes**. No documented or observed anonymous official Arc RPC method in this investigation provides authenticated pagination of one receipt. Increasing the event cap, ignoring unrelated funded proofs, restricting discovery to app bindings, or returning partial lifetime totals does not solve this.

The release gate remains open. No production source, Solidity/ABI, public protocol, financial policy, KDF, lockfile, migration, or Phase 5 evidence was changed. No suite was rerun and no historical counts or failed reports were rewritten. Exact inspected-source hashes, canonical 345-input comparison, preservation results, public RPC payloads and command evidence are in `dense-block-design.json` beside this report.

## One focused question and evidence boundary

Given arbitrary callers of the frozen contracts, when a block contains more than 16 target events, can repeated bounded private invocations eventually publish the complete block without weakening canonical history? The analysis first tests the highest-risk prerequisite: retrieval granularity. A database scheduler cannot repair an indivisible upstream response.

Executed: `python3 /home/deseti/.hermes/cache/scratch/retempo-phase6-dense/probe.py` (exit 0). This was a bounded **read-only public capability probe**, not a local staging/D1 implementation. Twelve anonymous JSON-RPC requests used only the official `https://rpc.mainnet.arc.io` endpoint, sequentially, with a 524,288-byte response limit (read one extra byte solely to detect overflow). No transaction submission, local/mainnet keys, credentials, paid resources, deployments, Git operations or owned server processes were involved. No provider CPU measurement is claimed. A workerd/D1 progress/restart prototype was deliberately not built: it would not settle the prerequisite that blocked a universal verdict.

## Current implementation findings

- `chain-worker/src/service.ts:25–68`: one shared **40 RPC/request** counter, 10-second fetch timeout, manual redirects, cancellation on decoded streamed response overflow. Configuration consumes **10 RPC calls**: chain ID, genesis, three code reads, four link reads, decimals. The later sync must share that budget; a new invocation does not inherit cached identity acceptance automatically.
- `indexer.ts:73–111`: a 60-second lease; 32-block initial range; whole-prefix halving on log response overflow or excess verification demand. A one-block result with more than 16 unique `(transactionHash, logIndex)` pairs refuses without advancing. `logs.length <= 256` is a separate raw duplicate envelope, not a complete-history guarantee.
- `indexer.ts:125–215`: receipts are deduplicated only inside an invocation. Each returned log is validated against its receipt and ABI round-trip; event blocks and the retained cursor are rechecked before one advancing `D1.batch`. This proves consistency of returned candidates, **not absence of silently omitted candidates** from `eth_getLogs`.
- `migrations/0001_chain.sql`: canonical events are append-only and a negative lease sentinel aborts a lost-lease batch through a CHECK constraint. Existing readers assume every stored event is canonical; there is no hidden staging generation.
- `history.ts`: indexed 64-event scope/keyset pages and exact payment-proof lookups, pinned to a complete cursor, binding hash, high-water and expiry. Publication visibility must apply to both page selection and exact proofs, not only final rendering. Pending staged rows must never influence high-water or `complete`.
- `projections.ts`: getters and history are pinned to the canonical cursor, including final rechecks. During staging the last fully published cursor can remain readable (complete **as of that cursor**, not current). Cold-start staging still has no published history. The 32-binding/26-getter admission envelope does not bound arbitrary contract callers, repeated events, transaction receipt size, or global event growth.
- `tests/capacity-restart-acceptance.ts` currently exercises the synthetic 17-event refusal surviving restart, then reduces the fixture to one event to recover. It is not proof of dense-block progress. `tests/indexer-overflow.test.ts` explicitly preserves the indivisible single-block/receipt refusal. These tests were inspected, not rerun or rewritten.

## Hard constraint: count scheduling is not retrieval pagination

1. `eth_getLogs` splits by block range and exact address/topics, not by transaction index, log index or byte offset. The final one-block query may still exceed the cap. Topic/address partitioning can be a fast path, but cannot guarantee termination: the frozen manager's `setPlanActive` and `setPlanPayout` can repeatedly emit `PlanUpdated` with the **same plan key and topic tuple**. Off-app merchant contracts need not obey admission limits. Splitting an exact topic value into every possible word is not a bounded operational solution and still does not split identical tuples.
2. `eth_getBlockReceipts` aggregates a whole block; it is a convenience path, not pagination. Per-transaction receipt retrieval helps with many small receipts but cannot split one oversized receipt.
3. A receipt includes **all transaction logs**, not just manager/escrow logs. An arbitrary wrapper can call its own Retempo merchant plan update and emit an unrelated large log in the same transaction. Filtering target events does not shrink the receipt required by the current verifier. Skipping other transaction senders/`to` addresses also misses internal calls and funded proofs.
4. Analytical size witness (not an executed EVM fixture): a single log with **262,144 data bytes** has **524,290 characters** in its `0x`-prefixed JSON hex data alone, already exceeding the **524,288-byte** envelope before receipt metadata or target events. Standard EVM LOG0 data gas alone is 2,097,152; memory expansion to 8,192 words is 155,648. The sampled block gas limit was 30,000,000. These calculations show why a small-receipt bound cannot be inferred from normal-looking traffic; they are **not a measured Arc admission result or a complete gas proof**. No deployed-chain rule limiting such receipts below the cap was established.
5. The standard false-block response still carries all transaction hashes. Its worst-case encoded size also needs a protocol-backed bound; the sampled gas limit alone is not a permanent bound on every future block or Arc/system-transaction behavior. Hash/index transaction lookup does not solve oversized input objects or supply an independent header.
6. An OK, well-formed truncated `eth_getLogs` array cannot be distinguished from a complete one by checking only returned receipts. Either retain an explicit trusted-provider completeness assumption and obtain a documented no-truncation/error contract, or enumerate all transaction receipts and check the reconstructed receipts root against the pinned header. A root mismatch must fail closed, never publish the subset. The latter still needs every entire receipt and Arc-compatible typed receipt serialization.

**Conclusion:** under an immutable 512-KiB total-response cap and the currently approved endpoint, no unconditional complete-history liveness proof was obtained. Repeated invocations solve finite work volume, not an indivisible response. This report does not claim oversized receipts were observed on mainnet, nor that every standard endpoint is mathematically incapable of a future proof-bearing extension.

## Conditional internal design for parent review

This preserves the public request/response shapes, ABI, financial semantics and 40-RPC counter. It requires future private schema/reader changes, expressly **not authorized or applied by this report**.

### State and identity

- `runtime`: existing complete public cursor/fingerprint/halt plus monotonically increasing lease epoch and active job ID. Lease ownership must be fenced at every write, not merely at acquisition.
- `block_job`: deployment fingerprint; generation/job ID; expected previous published `(number,hash)`; target `(number,hash,parentHash,timestamp,receiptsRoot,transactionsRoot)`; transaction count/manifest digest; retrieval/proof mode; phase; next transaction and receipt-log offsets; staged target count and digest; verification/retry state. One block at a time, next to the retained complete cursor (or configured start).
- `receipt_stage`: keyed by `(fingerprint,blockHash,transactionHash)` with ordinal, status, content digest, complete bounded raw receipt/buffer reference and next unprocessed log offset. Byte-identical retries are no-ops; conflicting content for the same identity fails closed. For a receipt spanning multiple event quanta, persist its raw bounded receipt once and resume decoding locally; do not repeatedly fetch the same receipt for every event chunk.
- `event_stage`: normalized target event body/digest, block generation and chain order. Uniqueness inside a generation is `(transactionHash,logIndex)`; existing outward ID remains `5042:transactionHash:logIndex`. Compare full bodies on conflicts. Do not use `INSERT OR IGNORE` to swallow contradictions. A reorg generation must not collide with the outward ID of an unpublished abandoned generation.
- `published_blocks`: immutable generation marker, complete manifest/root/digest, ancestry and counts. Staged payloads become visible only through this marker; no public DB financial write or shared authority flag is introduced.

### Transitions and atomic boundaries

1. **Discover / pin:** acquire fenced lease; validate deployment and retained cursor. Pin next block's hash and parent. Check transaction manifest/count, preserve order, and reject duplicates. At a nonzero start without an existing cursor, explicitly record the configured start-parent anchor rather than pretending an earlier public cursor exists.
2. **Retrieve / verify / stage:** use a bounded complete-log fast path where admissible, but dense fallback must enumerate **every transaction receipt**, not only receipts named by returned logs or admitted app bindings. Unrelated receipt data may be proof material; every recognized target event, including unrelated funded events, is retained. Status/identity/ordinal and all origin/ABI checks are mandatory. Failed transactions must not produce successful target financial events. Receipt-root serialization must account for actual Arc receipt types and system-emitted logs.
3. **Stage commit:** one atomic D1 batch checks live token/epoch/expiry, expected old published cursor, unchanged job phase and exact progress offset; inserts/compares the bounded receipt/event quantum; advances job offset/digest; renews lease. An explicit SQL guard must abort the **entire** batch on a stale owner or no-op CAS (a conditional UPDATE alone does not roll back unrelated inserts). Raw receipt persistence and its first progress offset are in the same transaction. Cancellation/failure before this commit leaves offsets unchanged; after commit, restart resumes at the durable offset.
4. **Complete coverage:** every manifest ordinal is processed exactly once; all receipt log offsets exhausted; all target events decoded and staged; bounded incremental root/digest verification completes. For protection from silent RPC omission, reconstruct `receiptsRoot` over all receipts and match the pinned header before readiness. This requires a reviewed restartable trie accumulator (private nodes/frontier, bounded node work per call), not one huge final CPU pass. Manifest count/order must also be checked; root reconstruction/transaction-root validation details are a separate unimplemented acceptance gate.
5. **Publish:** prepare fixed-size marker/CAS statements, revalidate target number/hash/parent and then the **retained old cursor as the final RPC**, immediately before the atomic D1 batch. The batch verifies live epoch/token/expiry, old cursor, job readiness/root/count/digest and inserts one publication marker while advancing cursor/fingerprint. Marker and cursor either both commit or neither does. No O(block-events) copying or `INSERT SELECT` is permitted in this final transaction.
6. **Read visibility:** future indexed event reads must include publication generation visibility in their **bounded candidate selection**, MAX/high-water and exact payment proof lookup; projections/getters remain pinned to the published cursor. Rowid/keyset progression cannot expose or count staging gaps or reorder old/new generations. A view over stage rows is not a proven drop-in replacement for the current `INDEXED BY events_*` queries. Preserve 64-event pages, binding/scope/cursor token invalidation and complete client exhaustion before totals. Existing tokens remain valid during hidden staging, and invalidate on publication as today.
7. **Cleanup:** only bounded indexed deletion of abandoned staging/proof buffers after publication, retaining required canonical events and proof metadata. GC is not part of publication correctness. TTL/storage exhaustion must suspend new staging explicitly, never delete published history to pretend progress.

### Lease, restart and reorganization policy

- A crash releases nothing implicitly: lease expires, new epoch takes ownership, durable offsets identify the next quantum. Stale holders cannot stage, publish, clear the new holder's lease or overwrite diagnostics. Same-token retries compare exact payloads. Lost final responses are recovered by reading the publication marker/cursor, not repeating financial writes.
- Revalidate the old cursor and staged target on **every resumed invocation**. Verify target parent equals the retained cursor hash for adjacent blocks. A changed unpublished block abandons the whole generation and restarts at that height only after the old published cursor is still canonical; never mix receipts across block hashes.
- A changed **published** ancestor keeps the current hard halt policy. Append-only financial proofs cannot be silently undone. Recovery/rebuild requires a separately reviewed isolated generation and atomic reader cutover; staging is not permission to relax this policy. Arc's advertised finality does not eliminate endpoint identity, lag or corruption checks.
- RPC/D1 cannot form one consensus transaction. Final canonical reads narrow, but do not eliminate, the precommit race. Preserve ongoing cursor checks after publication and report that trust boundary honestly.

### Conservative per-invocation envelope (proposal, not measured)

A simple safe initial dense quantum is **one newly fetched receipt** and at most **16 target event decodes** (or a bounded continuation of a previously buffered receipt). Large negative/unrelated receipt scans, manifest processing and trie accumulation also need bounded units, not just event count. Increase throughput only after provider CPU evidence.

Example worst-case fetch ledger for such a quantum: configuration 10 + initial old cursor 1 + pinned target 1 + optional count 1 + optional manifest 1 + receipt 1 + final target 1 + final old cursor 1 = **17 RPC**. Reserve final checks before work; an optional retry/failure consumes the same counter, with a hard maximum of 40. On a buffered continuation unnecessary RPCs can be omitted, not converted to unbounded work. A whole-block receipts fast path is optional and counts against the same cap; overflow cancels it and falls back on a later bounded step.

Target **at most 10 D1 API invocations** for the quantum (bounded individual statements/batches); even conservatively adding 17 RPC + 10 DB invocations stays below 50. Use a shared accounting ledger, not separate helper budgets. Serialize outgoing RPC and DB operations, drain/cancel streams before the next; configuration's three code reads have peak three connections, below six. Cap every response at 524,288 decoded bytes regardless of content length or compression. No unlimited recursive self-fetch, hidden batch RPC, or `waitUntil` budget multiplication.

Official [Workers limits](https://developers.cloudflare.com/workers/platform/limits/index.md) currently list Free 50 external subrequests, six simultaneous connections, 10-ms CPU and 100,000 requests/day; internal services have a separate 1,000-subrequest ceiling. Official [D1 limits](https://developers.cloudflare.com/d1/platform/limits/index.md) list 50 queries per Free invocation, 500-MB database, 5-GB account storage, 2,000,000-byte row/string/blob, 100 parameters and 100,000-byte SQL. **The current D1 page explicitly counts a `db.batch()` as one query for the invocation limit**, although individual statements retain their other limits. Do not confuse these with 50 total Worker invocations per day or assume arbitrary batch work fits CPU. The conservative proposed DB/RPC sum is stricter than those separate service buckets; actual instrumentation and the dedicated account remain gates.

One bounded receipt buffer fits the documented D1 row limit, but aggregate job/event/root state and indefinite canonical history do not have unlimited Free storage. No local wall clock is provider CPU. A 16-event quantum is a work limit, not proof of 10-ms compliance. Need approved scheduling/backoff and measured arrival/catch-up/storage budgets: finite-block termination is not sustained throughput. Reading old complete history during backlog must not be described as up-to-head settlement.

## Minimal choices / owner decisions

1. **Keep all existing bounds and endpoint:** approve only a conditional staging implementation, clearly retaining the single-object retrieval and complete-history release blockers. This is not sufficient for unrestricted financial launch. Tenant admission and a traffic forecast cannot turn it into a guarantee.
2. **Keep 512 KiB, obtain a stronger retrieval capability:** require a provider-documented bounded receipt/log-page protocol with complete manifest, header/root binding and continuation identity (and a non-oversized header path). Probe official support and historical retention before selection. Merely accepting unknown `limit`/`offset` fields is not evidence; servers can ignore them. An external relay/archival proof service requires a separate architecture/trust/endpoint approval and actual resource/cost feasibility. None was provisioned or presumed free.
3. **Reconsider the total-response bound, not just the event cap:** if the owner permits a bounded streaming verifier to consume complete larger responses, establish a chain/protocol-backed maximum for receipt/header size, resource metering and retry behavior, with incremental persisted verification and hosted CPU proof. This changes an existing resource policy and is **not authorized here**. A larger arbitrary cap alone still offers no worst-case proof.
4. If no eligible bounded retrieval source exists and the bound cannot change, **defer the financial public release**. Changing contracts/admission semantics to enforce chain-wide maxima would require renewed scope/ABI/policy approval and is outside the frozen implementation; app-only limits cannot enforce it.

No choice silently authorizes paid plans, third-party credentials, remote writes, mainnet broadcasting, skipped history, or reduced escrow functionality. Parent review should select a retrieval decision **before** investing in the larger staging architecture.
