# Private verified-chain service

This Worker owns **only** `CHAIN_DB`. The public Worker must use its private `CHAIN` service binding, never bind this database. `workers_dev=false`, `preview_urls=false`, `routes=[]`; there are no production IDs or resources. No deploy has been performed.

Configuration is intentionally empty. All five optional runtime variables must be supplied together: `APP_ENV`, `ARC_RPC_URL`, `ARC_MANAGER_ADDRESS`, `ARC_ESCROW_ADDRESS`, `ARC_START_BLOCK`. Missing variables return `configured:false`, `mode:disabled`, null addresses. Explicit development/test permits a loopback RPC; production accepts only the currently documented primary `https://rpc.mainnet.arc.io/` endpoint. The official explorer is `https://explorer.arc.io`. Production also requires `ARC_EXPECTED_GENESIS_HASH`, `ARC_EXPECTED_MANAGER_CODE_HASH`, and `ARC_EXPECTED_ESCROW_CODE_HASH`, each a reviewed bytes32 hash compared against actual RPC state. Loopback development/test does not require pins. These checks do not independently audit deployed code. No URL credentials, query strings or fragments are permitted or exposed. The fixed chain ID is 5042 and token is six-decimal `0x3600000000000000000000000000000000000000`. Local fixture addresses are never production defaults. Configuration verifies chain ID, genesis, code at manager/escrow/token, reciprocal links, USDC address and decimals; returns genesis/code hashes for wallet-world comparison.

## Wire protocol and binding requirements

Exactly `shared/chain.ts`: GET `/v1/config`, POST `/v1/bind`, POST `/v1/sync` with `{}`, POST `/v1/snapshot` with `{orgId}`. Unknown authority/status/log/RPC fields are rejected. This is a private service boundary, not public-user authentication.

Binding keys are independently recomputed using the same formulas as `worker/src/chain/keys.ts`:

- `reference(orgId,kind,recordId) = keccak256(UTF8(JSON.stringify(['retempo:v1',orgId,kind,recordId])))`.
- Plan key: `keccak256(abi.encode(merchant,reference(orgId,'plan',planRecordId)))`.
- Subscription key: `keccak256(abi.encode(customer,reference(orgId,'subscription',subscriptionRecordId)))`.
- Invoice/payment key: `keccak256(abi.encode(subscriptionKey,uint256(chargeNumber)))`.
- Escrow key: `keccak256(abi.encode(merchant,invoicePaymentKey))`.

Bind the plan first; subscription requires customer and a matching tenant-owned planKey. Invoice/payment/escrow require an existing matching subscription, planKey, subscriptionKey, customer, canonical positive uint32 chargeNumber and uint128 decimal amount. Immutable identity includes all supplied optional fields; retries must preserve them. Amount and chargeNumber must be JSON decimal strings, never numbers; metadata must be an object of string/boolean/null values. Migration `0002_unique_binding_identity.sql` enforces one record per `(kind,key)`: one charge may back one invoice and one payment, never two invoices or two payments. Migration deliberately fails on pre-existing duplicates rather than selecting an identity silently. Addresses/hashes normalize lowercase; metadata is not used as settlement evidence. Conflicting org/key/wallet/record reuse fails. Bindings are allowed before transactions, but do not create paid projections.

## Exact read-model normalization

All projection values are strings, booleans or null. Numeric contract fields and base-unit amounts are decimal strings; address/hash strings lowercase. `blockNumber` is decimal; verified event `timestamp` is canonical ISO-8601 from the canonical block.

- **plan:** state/values.status `pending | active | inactive`; flattened getPlan fields (amount, payout, interval, trial, grace, vestDuration, arbitrator, customerMayRefundUnvested, active, merchant).
- **subscription:** state/values.status `pending | active | canceled`; flattened getSubscription fields including decimal chargeCount and acceptedArbitrator; `nextChargeAt` ISO/null.
- **mandate:** same binding recordId/key as subscription, kind `mandate`; state/values.status `missing | active | expired | revoked`; perChargeCap/totalCap/spent/nonce decimal strings, active boolean, expiry ISO/null. Expiration compares the pinned indexed block timestamp, not browser wall time.
- **invoice/payment:** state/values.status `pending | paid`; amount and chargeNumber from immutable binding; paidAt ISO/null, transactionHash hash/null, periodStart and nextChargeAt ISO/null. **Only** a stored independently receipt-verified matching SubscriptionPaymentProcessed (subKey, planKey, customer, merchant, chargeNumber and amount) can produce paid. getSubscription.chargeCount alone cannot.
- **escrow:** state/values.status `missing | pending | active | closed | cancelled`; all flattened getEscrow fields. Claimed/awarded/refunded/frozen/carvedVested/amount stay decimal strings. `balance` is the actual pinned `balanceOf(key)` and `claimable` the actual pinned `claimableAmount(key)`, not reconstructed vesting math. vestStart, vestEnd, disputedAt, respondBy, resolveBy are ISO/null; vestDuration/responseWindow/resolutionTimeout are decimal durations. `dispute = none | open | resolved`; `outcome = none | fully_vested | refunded | resolved | expired | settled`.
- **dispute:** same escrow recordId/key and values; only present when dispute != none; state `open | resolved`.
- **ledger:** stable recordId = verified event ID, exactly one projection per economic event. values include `{kind,direction,amount,counterparty,createdAt,transactionHash,eventName}` plus raw normalized args. Payment (`kind:payment`, direction `in`) comes from SubscriptionPaymentProcessed or **direct** EscrowFunded(viaManager=false); manager-routed EscrowFunded is not another payment. `claim/in` comes from VestedClaimed; `refund/out` only from RefundCredited; `award/in` only the merchantAmount from DisputeResolved/Expired/SettlementAccepted. Zero amounts are omitted. These credits are **not** wallet withdrawals. Never sum payment, claim and award as gross revenue together.

Wallet-wide Withdrawn/PayoutAddressUpdated have no tenant provenance: they remain in the private canonical store but are deliberately **omitted from every tenant snapshot and payout ledger**. No per-org withdrawal allocation is invented, even when the current binding set contains only one org. Their attribution needs an explicitly approved complete credit-provenance policy.

`POST /v1/wallet-snapshot` accepts exactly `{wallet: validAddress}` and returns a `ChainSnapshot` with empty bindings and only durable escrow `Withdrawn`/`PayoutAddressUpdated` events whose normalized `args.account` equals the normalized wallet. Each event has one `kind:wallet` projection: `recordId=wallet`, `orgId=wallet:${wallet}`, zero-left-padded address as bytes32 key, `state:updated`, original block/transaction and raw args plus eventName/timestamp/createdAt/transactionHash. Multiple events intentionally share the wallet recordId; distinguish proofs by the returned event IDs or transaction/event identity, not recordId alone. The same canonical cursor, fail-stop and complete-history limit apply. This private endpoint provides action confirmation only, not tenant bookkeeping; the public bridge must authenticate SIWE ownership before requesting it. No arbitrary-wallet public route is implemented here.

## Persistence, safety and limits

A scan starts with at most 32 blocks and halves its complete prefix until at most 256 returned logs, 16 unique events and the remaining RPC budget fit. It retries at most six log ranges. A single block that cannot fit returns HTTP 503 with an explicit capacity error and leaves the cursor/events unchanged; no partial block is committed or silently skipped. Every returned manager/escrow log is checked for address, exact canonical ABI re-encoding, bounds, canonical block hash, successful matching receipt, exact receipt-log contents, transaction hash/index and log index. USDC Transfer is never a business source. Unknown/unbound canonical events remain private until an immutable matching binding exists. Append-only event triggers reject UPDATE/DELETE/REPLACE; dedup ID is `(5042,txHash,logIndex)`.

A D1 lease serializes scans. The commit batch has a CHECK-backed ownership guard, event inserts and cursor/fingerprint update atomically; loss of lease or any partial RPC/receipt failure stores no partial events and does not advance the cursor. An expired lease can be retried after process death. Cursor/deployment fingerprint mismatches persist `runtime.halted`; restoring an old RPC world does not silently resume. No automatic reorg deletion/reset endpoint exists. Recover only through an explicitly reviewed operator workflow into an isolated database; never toggle a public financial authority flag.

Snapshots return complete tenant-bound history within a global 256-canonical-event MVP safety bound. A 257-row sentinel makes the service return HTTP 503 with an explicit complete-history-unavailable error; it never presents latest-N history as all-time totals. Money is never SQL-cast or SUMmed. Snapshots use canonical indexed-block getters, recheck the block after reads, and project from the durable append-only store, so late binding and repeated/restarted readers do not duplicate ledger/payment rows. Snapshot projections are deterministically rebuilt, not mutable client-provided records.

### Phase 5 request and admission envelope

- One request shares a hard **40 RPC call** counter across configuration (10 calls), sync and snapshots. Responses expose `x-chain-rpc-calls` and `x-chain-rpc-limit`. Redirects are manual and non-OK responses fail closed; an RPC response is streamed with a 512 KiB maximum before JSON parsing. Existing receipt caching fetches one receipt per transaction, not per event. Canonical rechecks and atomic commits remain mandatory.
- Existing-event reads are one D1 batch (up to 16 SELECT statements), not per-event invocations. A successful nonempty scan uses six D1 invocations including lease release. Thus the conservative combined ceiling is 46 RPC + D1 invocations, below 50. Configuration performs at most three outgoing RPC requests concurrently; other RPC operations are sequential and response bodies are consumed. Fixture tests independently count real D1 calls and RPC calls; they are not Cloudflare production billing observations.
- Tenant snapshots have at most **32 bindings** and **26 distinct pinned getter calls**. Plan getters are shared by key, subscriptions use subscription + mandate + shared plan, and escrows use getEscrow + balanceOf + claimableAmount. Snapshots preflight the full getter inventory before any getters. No terminal-state cache, persistent getter cache or invented vesting math was introduced.
- Migration `0003_binding_capacity.sql` enforces both tenant limits inside the same atomic binding batch, including competing admissions. It refuses a new binding before wallet submission should be permitted; accepted bindings remain readable within the history bound. Idempotent existing bindings still succeed at capacity. For one plan and one subscription, seven distinct escrow charge bindings fit (24 getters); an eighth is refused (27). Without escrows, two base bindings plus 30 payment bindings reach the 32-binding ceiling. Public callers must propagate a failed bind/preparation before wallet approval/submission. This private change cannot by itself police direct contract transactions.
- A scheduled **read-only** sync entry point uses the identical budgeted verifier only when `ARC_SYNC_CRON_ENABLED` is exactly `true`; default configuration is `false`, with no triggers. Production identity pins still apply. Operational failures log only a fixed code and message, never RPC URLs, request bodies or exception details. No funded recurring executor or signing key was added. An operator may consider a five-minute trigger only after production CPU acceptance and resource authorization.

**Remaining production gates:** these deliberately small limits are a bounded local MVP, not unrestricted production readiness. The global history bound was reduced from 5,000 to 256 to bound reconstruction work; it is an explicit unavailability gate, not pagination. Additional events from previously accepted bindings or direct onchain users can eventually cross it despite admission quotas, after which snapshots fail rather than reporting fake totals. Complete-history pagination/materialization and an agreed growth/admission policy are required before an unrestricted launch. Oversized pre-migration tenants remain unavailable explicitly; the migration does not rewrite their financial identities. Dense single blocks may also require a reviewed larger-capacity or partial-block protocol. CPU-heavy ABI checks, code hashing and snapshots still require **actual Cloudflare Free 10 ms CPU** validation for both HTTP and cron. Local elapsed time is not CPU billing evidence. Daily request/read/write/storage quotas, production RPC behavior, custody-approved identity hashes and operational reorg recovery also remain release gates. No deployment, account change, paid plan, mainnet transaction or production CPU proof is claimed.
